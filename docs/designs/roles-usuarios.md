# Design: Roles y usuarios del panel (admin / operador)

## Problem Statement

Javier (cooperativa) quiere crear él mismo las cuentas del panel para su gente, con dos roles:
**admin** (acceso a todo) y **operador** (solo funciones básicas que no puedan romper el sistema),
sin pasar por nosotros.

Hoy eso es imposible y además sería peligroso:
- No hay endpoint ni pantalla para crear una segunda cuenta: la única fila de `admin_users` la
  crea el seed con `ADMIN_EMAIL` (`db/seed.ts:203`).
- `role` se guarda (`schema.ts:209`) y viaja en el JWT, pero **no se consulta para autorizar en
  ningún lado**: `requireAdmin` (`auth/adminAuth.ts`) solo valida el token. Toda cuenta que entra
  puede todo, incluido marcar una patente como remis ($500 en vez de $8.000) (ADR-055).
- La cuenta por defecto tiene prohibido reconciliar (`paymentService.ts:560`, por email) ⇒ si hoy
  se cuelga un pago real, **nadie en la cooperativa lo puede destrabar** (ADR-054).
- Un JWT vale 12 h aunque se borre la cuenta, y `verifyToken` toma el `role` del token, no de la
  base (`adminService.ts:57`).

Esto cierra el ítem 🔴 BLOQUEANTE de C1 en `TODOS.md` y el pendiente C1 de `pendientes-manual.md`.

## Decisiones de la sesión

- **Qué se da de alta:** cuentas del panel (email + clave + rol). La carga de patentes de socios
  ya existe y no cambia de forma, solo de permiso.
- **Operador y patentes:** solo lectura. Una patente mal cargada como remis rompe el anti-abuso
  de tarifas; Javier (admin) las carga él.
- **Admin y lo técnico:** la clave del ESP32 y los ajustes técnicos quedan en un tercer rol,
  `tecnico`, **solo para Insolva; visible para la cooperativa pero intocable** (gate de /autoplan). Rotar la clave del ESP32 deja
  la máquina parada hasta reprogramarla en sitio.
- **Enfoque B (mapa de permisos compartido)** sobre A (niveles por ruta: el panel repetiría la
  lógica y se puede desfasar) y C (sesiones en base: rehace un login que funciona; la revocación
  se logra con un chequeo en base por pedido).

## Premises (aceptadas)

1. Tres roles en el sistema, dos visibles: `tecnico` (Insolva, la cuenta del seed), `admin`,
   `operador`. Un admin ve y asigna solo admin/operador.
2. El permiso lo decide el servidor, acción por acción (403 aunque se arme el pedido a mano).
   Ocultar botones es comodidad, no protección.
3. La matriz de abajo.
4. Desactivar, cambiar rol o resetear clave corta la sesión en el acto: cada pedido chequea en la
   base que la cuenta siga activa y que el `token_version` del token coincida con el de la fila.
5. Nadie se deja afuera: nadie puede desactivarse ni cambiarse el rol a sí mismo, y siempre queda
   al menos un admin activo. Un admin **sí** puede editar o desactivar a otro admin, dentro de
   esa regla.
6. Sin mails: el admin pone la clave inicial y la puede resetear; cada uno cambia la suya en
   "Mi cuenta".
7. La cuenta técnica no destraba pagos (conserva el objetivo del ADR-054: nombre de una persona
   de la cooperativa en la auditoría). La regla pasa de "email == ADMIN_EMAIL" a "rol == tecnico".

## Matriz de permisos

Una sola tabla en `packages/shared` (`permissions.ts`): `Permiso → roles`. La usan la API
(`requirePermission(p)` por ruta) y el panel (`can(p)` para menú y botones).

| Permiso | Rutas actuales | operador | admin | tecnico |
|---|---|:-:|:-:|:-:|
| `panel.ver` | GET overview, machines, machines/:id, qr, devices, sessions, sessions/:id, payments, logs, vehicles, settings | ✓ | ✓ | ✓ |
| `pagos.destrabar` | POST sessions/:id/reconcile/auto y /manual | ✓ | ✓ | ✗ (premisa 7) |
| `maquina.parada_emergencia` | POST machines/:id/emergency-stop | ✓ | ✓ | ✓ |
| `patentes.editar` | POST vehicles, DELETE vehicles/:plate | ✗ | ✓ | ✓ |
| `maquina.configurar` | PATCH machines/:id (tarifas, duración, habilitar, nombre) | ✗ | ✓ | ✓ |
| `ajustes.negocio` | PATCH settings → solo `dailyWashLimit` | ✗ | ✓ | ✓ |
| `ajustes.tecnicos` | PATCH settings → `demoSpeedFactor`, `authTtlSeconds`, `heartbeatIntervalMs`, `paymentPendingTimeoutSeconds` | ✗ | ✗ | ✓ |
| `dispositivo.rotar_clave` | POST devices/:id/rotate-secret | ✗ | ✗ | ✓ |
| `usuarios.gestionar` | nuevas rutas de usuarios (abajo) | ✗ | ✓ (solo admin/operador) | ✓ (todos) |

`PATCH /settings` pasa a chequear permiso **por campo**: un pedido que trae un campo técnico
sin `ajustes.tecnicos` responde 403 entero (no se aplica a medias).

## Cambios

**Base (migración `0003_admin_roles.sql`, a mano como la 0002 — el journal de drizzle-kit está
desincronizado, ver `TODOS.md`; SQL que corra igual en PGlite y en Postgres):** `admin_users`
suma `name` (texto), `active` (bool, default true) y `token_version` (int, default 0). `role`
queda texto con valores `tecnico | admin | operador`, **default `operador`** (el menor privilegio).
La migración pasa **todas las filas existentes** a `tecnico`: el SQL no puede leer `ADMIN_EMAIL`,
y hoy todas las cuentas son de Insolva (incluidas las que queden de un `ADMIN_EMAIL` anterior).

**Seed (`db/seed.ts`):** crea la cuenta de `ADMIN_EMAIL` como `tecnico` (hoy la inserta como
`admin`, línea 207). La clave de la cuenta técnica la sigue mandando `ADMIN_PASSWORD` (es la
forma documentada de rotarla); cuando el seed cambia el hash (sync de `ADMIN_PASSWORD` o el
bloqueo de la clave demo en producción, `seed.ts:219-231`), incrementa `token_version`. Por eso
**"Mi cuenta" no ofrece cambiar clave a la cuenta técnica**. Se quita el warning de "otras cuentas
admin" del arranque (línea 235): ahora es lo normal.

**Auth:** el JWT lleva `sub` = id de usuario y `tv` = token_version. `requireAdmin` pasa a ser
async y busca la fila en cada pedido: si no existe, está inactiva o `tv` no coincide ⇒ 401. El
`role` sale de la base, nunca del token. **Tokens emitidos antes del deploy** (`sub` = email, sin
`tv`) ⇒ 401: todos vuelven a iniciar sesión una vez (con test). Desactivar, cambiar rol o resetear
clave incrementa `token_version`. Login de una cuenta inactiva ⇒ el mismo error genérico que una
clave incorrecta. `req.admin` pasa a ser `{ id, email, name, role }`.

**Rutas nuevas (`usuarios.gestionar`):** `GET /admin/users` (incluye las cuentas `tecnico`,
marcadas como "Soporte técnico (Insolva)"), `POST /admin/users` (email, nombre, rol, clave inicial
≥ 10 caracteres), `PATCH /admin/users/:id` (nombre, rol, activo, resetear clave). Reglas del
servidor: un admin **ve** las cuentas `tecnico` pero no las puede crear ni modificar (403); nadie
se cambia el rol ni se desactiva a sí mismo; **ningún cambio puede bajar
la cantidad de admins activos de 1 o más a 0** (así la regla no bloquea el arranque, cuando hay
cero); email ya existente ⇒ 409; en producción se rechaza `DEMO_ADMIN_PASSWORD` como clave
(si no, el seed la cambiaría sola al reiniciar).
**Para todos (salvo técnico, ver seed):** `PATCH /admin/me/password` (clave actual + nueva), con
su **propio** rate limit (misma medida que el login, 10 intentos cada 15 min, pero contador
aparte para no gastar el cupo del login); incrementa `token_version` y
**devuelve un token nuevo** para no echar a quien la cambió. `GET /auth/me` devuelve
`{ email, name, role, permissions }`.

**Cuenta técnica visible (User Challenge 1, decidido por Pablo en el gate de /autoplan):** la
cooperativa la ve en Usuarios y su mail real en los registros; no se enmascara nada. `getSettings`
sigue devolviendo `adminEmail`. Pablo le avisa a Javier que la cuenta existe y para qué.

**Reconciliación:** se borra el chequeo por email (`isDefaultAdmin`, `paymentService.ts:560`), el
resultado `default_admin_forbidden` y su manejo en el panel web; la única barrera es el permiso
`pagos.destrabar` en la ruta (403). Contrato único para tests y panel. `reconcilePayment*` recibe
el principal, no solo el email.

**Auditoría:** el `actor` sigue siendo el email (único y estable); el nombre se muestra al lado en
el panel. Eventos nuevos: `USER_CREATED`, `USER_UPDATED` (qué cambió, sin claves),
`USER_PASSWORD_RESET`, `PASSWORD_CHANGED`, `PERMISSION_DENIED` (actor, permiso, ruta).

**Panel:** menú y botones según `can(permiso)`; página **Usuarios** (lista, alta, editar rol /
activar / resetear clave); página **Mi cuenta** (cambiar clave). Un operador ve las patentes sin
botones de alta/borrar y los ajustes en solo lectura.

## Success Criteria

- Test que recorre la matriz completa: cada ruta × cada rol ⇒ 2xx o 403 según la tabla, entrando
  por el login real (no con `issueToken()` directo, lección del ADR-054).
- Desactivar a un operador ⇒ su siguiente pedido responde 401, sin esperar 12 h.
- Un token viejo (anterior al deploy) ⇒ 401. Cambiar la propia clave no echa a quien la cambió.
- La cuenta técnica aparece en Usuarios como "Soporte técnico (Insolva)", sin acciones.
- Un admin no puede: editar/desactivar cuentas técnicas, desactivarse, dejar cero admins, tocar
  campos técnicos de ajustes, rotar la clave del ESP32.
- La cuenta técnica no puede destrabar pagos; un operador sí, y su nombre queda en la auditoría.
- En producción: Javier crea un operador desde el panel y ese operador destraba un pago simulado.

### Especificación del panel (agregada por esta revisión)

**Alta de usuario (Javier crea a un operador):**
```
Usuarios ──[+ Nuevo usuario]──> Formulario ──[Crear]──> Pantalla "Cuenta creada" ──> Usuarios
            nombre, email,         (409 inline         email + clave inicial +
            rol, clave inicial      "Ya existe")       [Copiar] [Enviar por WhatsApp]
            (≥10, mostrar/ocultar,                     "Al entrar la primera vez le vamos
             [Generar una])                             a pedir que la cambie."
```
- Columna nueva `must_change_password` (bool, default true al crear o resetear): el primer login lleva directo a
  Mi cuenta, con el resto del panel bloqueado hasta cambiarla (el servidor responde 403 `PASSWORD_CHANGE_REQUIRED` a todo
  menos `/auth/me` y `/admin/me/password`).
- "Enviar por WhatsApp" = link `https://wa.me/?text=...` con email, link al panel y la clave; lo elige Javier.

**Lista de Usuarios:** tabla en escritorio / tarjetas en celular. Orden: activos por nombre, inactivos al final
atenuados. Por fila: nombre (+ "(vos)" en la propia), email, badge de rol, estado. Una sola acción primaria:
"+ Nuevo usuario". Vacío: "Todavía no hay más cuentas. Creá la de tu primer operador."

**Acciones sobre un usuario** (menú de la fila): editar nombre/rol, desactivar/reactivar, resetear clave. Confirmación
que nombra la consecuencia ("Pedro queda afuera del panel en el acto"). Las acciones prohibidas (sobre uno mismo, dejar
cero admins) se muestran **deshabilitadas con el motivo**, no fallan después de apretar.

**Mi cuenta:** nombre, email y rol (solo lectura) + cambiar clave (actual, nueva ≥ 10, mostrar/ocultar). Errores:
clave actual incorrecta, 429 "Demasiados intentos, probá en 15 minutos". Éxito: aviso breve, sigue logueado (token
nuevo). La cuenta técnica ve la sección de clave reemplazada por "La clave de esta cuenta se gestiona desde el servidor".

**Menú:** el nombre y el rol de quien entró van en un chip arriba (escritorio y celular); ahí adentro, Mi cuenta y
Salir. Usuarios va al final del menú, solo para quien tiene `usuarios.gestionar`. Mientras `/auth/me` no respondió, el
menú muestra un esqueleto: nunca se dibujan acciones antes de saber el rol.

**Sin permiso:** las acciones que el rol no puede hacer **no se muestran**. Las pantallas con partes de solo lectura
(Patentes para operador, Ajustes para admin) muestran los datos como texto plano con una línea arriba: "Solo un
administrador puede cambiar esto." Si igual llega un 403 (pestaña vieja, rol cambiado), el mensaje va al lado de la
acción, no en pantalla completa, y no se borra lo que la persona había escrito.

**Sesión cortada:** el 401 lleva un motivo (`inactive`, `session_changed`, `expired`) y el login muestra un aviso:
"Tu cuenta fue modificada por un administrador. Volvé a entrar." / "Tu sesión venció." El día del deploy aplica el
mismo aviso (`session_changed`). Cambio en `apps/web/src/api/client.ts:36`, que hoy redirige sin decir nada.

**Accesibilidad:** objetivos táctiles ≥ 44 px (como el resto del panel), etiquetas en todos los campos, foco al primer
error del formulario, badges de rol con texto (no solo color).

### Correcciones al plan (todas incorporadas; las 4 primeras habrían roto el build)
1. **`requireAdmin` async en Express 4:** envolver con `ah()` o try/catch → `next(err)`; si no, un error deja el pedido colgado.
2. **`must_change_password` DEFAULT false** en la migración (con true, la cuenta técnica, que no puede cambiar clave en
   la app, quedaba bloqueada para siempre y nadie podía crear a Javier). Se pone true explícito al crear/resetear.
3. **Manejo del 401 en la web** (`client.ts:36`): clave actual incorrecta en "mi clave" devuelve **400**
   `INVALID_CURRENT_PASSWORD`, no 401 (un error de tipeo no echa a nadie); se limpia el token solo si es el mismo que
   usó el pedido (un poll viejo en vuelo no borra el token nuevo); `/admin/auth/me` deja de estar excluido del redirect
   (solo `/admin/auth/login`), así un usuario desactivado no queda en el esqueleto para siempre.
4. **`SettingsPage.tsx:50` manda los 5 campos siempre:** con chequeo por campo, todo guardado de un admin daría 403.
   Pasa a mandar solo lo cambiado y permitido.
5. **Carrera "último admin":** dos admins desactivándose a la vez podían dejar cero. Un solo `UPDATE` condicional
   (`... WHERE (SELECT count(*) ... role='admin' AND active AND id <> $1) >= 1`), con test `Promise.all`.
6. **Mass assignment:** schemas `.strict()`; `tokenVersion` y `mustChangePassword` nunca vienen del cliente.
7. **Emails:** `trim().toLowerCase()` en el zod al crear y al loguear (hoy el login normaliza y el alta no lo haría).
8. **Enumeración en el login:** si el email no existe, correr un scrypt ficticio; verificar la clave antes de mirar `active`.
9. **JWT:** fijar `algorithms: ['HS256']`; `tv` numérico obligatorio.
10. **Migración en transacción** (`migrate.ts` no envuelve archivos): `BEGIN/COMMIT` + `IF NOT EXISTS`; también cambiar
    el default en `schema.ts`.
11. **Seed:** el sync de clave por `ADMIN_EMAIL` solo si esa fila es `tecnico` (si no, pisaría la clave de un usuario
    creado por Javier con ese mail); `token_version` también en el bloqueo de clave demo.
12. **Enmascarado en logs: descartado** (User Challenge 1 → cuenta técnica visible, mail real en los registros).
13. **`PERMISSION_DENIED`** se audita solo en pedidos que modifican (los GET son de todos; evita inundar la auditoría
    desde una pestaña vieja).
14. **Rate limit de "mi clave" por id de usuario**, no por IP (la cooperativa comparte una IP).
15. **Id técnico modificado por un admin → 403** (la cuenta es visible; no hay nada que ocultar).
16. **Tests que se rompen y cómo:** `reconciliation.test.ts:21` (tokens de emails sin fila → 401: crear filas y entrar
    por login), `reconciliation.test.ts:275-288` y `mesa-de-entrada.test.ts:80` (`default_admin_forbidden` → 403),
    `mesa-de-entrada.test.ts:137` (12 h → invertir: ahora 401), `seed.test.ts:54` (warning quitado).

### Riesgos aceptados y documentados
- **Un admin puede resetear la clave de otro admin y entrar como él**: el nombre en la auditoría no es prueba absoluta
  entre admins. A esta escala (Javier + 1) es aceptable; se deja escrito.
- **`/api/demo/*` sin login mientras `DEVICE_SIMULATOR=true`** (hoy en producción, a propósito, ADR-048). No lo agrega
  esta fase; apagar el simulador antes del ESP32 real ya está en ESTADO (D1).
- **Rollback:** el código viejo ignora `active` y `role` → un operador o un usuario desactivado tendría acceso total
  tras un revert. Procedimiento: antes de revertir, desactivar a todos los no técnicos borrando sus filas (Choice 3 en
  el gate: alternativa = al desactivar, también reemplazar el hash de la clave).
