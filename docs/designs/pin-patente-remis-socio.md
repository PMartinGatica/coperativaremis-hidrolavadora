# Design: PIN de 4 dígitos por patente (remis/socio)

## Problem Statement
Gaby (representante de la cooperativa cliente) pidió, mirando el producto funcionando en
vivo, que cada patente remis/socio tenga un PIN de 4 dígitos — hoy cualquiera puede escribir
la patente registrada de otra persona y cobrarse la tarifa preferencial ($500 remis / $2.000
socio) en vez de la de particular ($8.000), porque nada verifica que quien la carga sea su
dueño real.

## Diagnóstico (Q1-Q3 del modo startup, ya contestadas — smart-skip)
- **Demanda real (Q1):** Gaby lo pidió en vivo, viendo el flujo real, no una idea hipotética.
- **Status quo (Q2):** hoy CUALQUIERA que sepa una patente ajena (remis o socio) se cobra su
  tarifa preferencial — cero fricción, cero verificación.
- **Persona concreta (Q3):** Gaby, quien valida el sistema por la cooperativa.

## Corrección de alcance (durante la confirmación de premisas)
Mi primer modelo asumía "1 PIN por patente" (fila de `vehicles`). El usuario corrigió: el
PIN es **de la persona**, que puede tener 2 autos — su remis (cooperativa, $500) y su
particular (que por ser socio cobra $2.000, no $8.000) — usando el MISMO PIN para ambos.
Confirmado además que "cuántos lavados le quedan hoy" **ya existe** en
`MachinePage.tsx:402-403` (`quote.remainingToday`, ya calculado en `quotePlate()`) — cero
trabajo ahí, ya está construido.

## Premises
1. El PIN es prueba de posesión, no identidad fuerte — alcanza para frenar a alguien que
   memoriza una patente ajena, no fraude sofisticado.
2. Cotización (`/quote`) y cobro (`/sessions`) SIEMPRE muestran y cobran el mismo precio —
   nunca mostrar $500 y cobrar $8.000 (o viceversa) por una diferencia de cuándo se valida
   el PIN. Ambos endpoints corren la MISMA función de resolución de categoría/precio.
3. Las patentes remis/socio que YA existen en la base (2 demo + las reales que cargue el
   dueño) no tienen PIN hoy — el rollout no puede dejarlas bloqueadas de un día para el otro.
   **Grandfather clause:** una fila sin PIN seteado sigue funcionando exactamente como hoy
   (sin pedir PIN) hasta que alguien le asigne uno.
4. El PIN se guarda hasheado (scrypt + salt, timing-safe compare), reusando
   `hashSecret`/`verifySecret` de `apps/api/src/db/seed.ts` (mismo mecanismo que ya usa la
   contraseña de admin) — no se inventa un mecanismo nuevo.
5. El cupo diario (ADR-024, 2 lavados por patente) no cambia — cuenta por patente literal,
   igual que hoy (`idx_sessions_plate_created`); el PIN afecta el PRECIO, no el conteo.

## Approach elegido: PIN por fila de `vehicles`, mismo valor en las 2 patentes de una persona
Sin entidad nueva. Se agrega una columna `pin` (hash) a `vehicles`, que ya existe. Cuando el
dueño registra las 2 patentes de una misma persona (su remis + su particular), escribe el
MISMO PIN de 4 dígitos en ambas filas — es disciplina de carga en el admin, no una relación
de base de datos nueva. Reusa el 100% de lo ya construido (`VehiclesPage.tsx`,
`categoryAndPriceOf`, `getVehicleByPlate`).

**Alternativa descartada (entidad "socio" con FK a patentes):** más prolija a prueba de
errores de carga, pero es un modelo de datos nuevo (migración, UI de gestión de socios
separada de patentes) para ~2-3 socios con 2 autos cada uno hoy. Descartada por
desproporcionada al tamaño real del problema (P3 pragmático) — se revisita si la cooperativa
crece a un volumen donde la carga manual del mismo PIN 2 veces se vuelva un problema real.

## Plan de implementación

### 1. Dominio (`packages/shared/src/types.ts`, `apps/api/src/db/schema.ts`)
- `vehicles.pin: text('pin')` — nullable, guarda el hash (`hashSecret()`), nunca el PIN en
  claro. Migración vía `npm run db:generate -w @hidro/api` (no a mano — evita desincronizar
  `meta/_journal.json`).
- `VehicleRow` (shared types): agrega `hasPin: boolean` — el frontend nunca recibe el hash,
  solo si existe o no.

### 2. Validación (`packages/shared/src/validation.ts`)
- `PlateBodySchema`: agrega `pin: z.string().regex(/^\d{4}$/).optional()` — mismo schema
  sirve para `/quote` y `/sessions` (DRY, ya lo comparten hoy).
- `VehicleUpsertSchema`: agrega `pin: z.string().regex(/^\d{4}$/).nullable().optional()`
  (corregido tras Eng review — `.optional()` solo acepta `undefined`, rechaza `null`, y el
  plan necesita `null` para el borrado explícito). **Semántica
  explícita:** campo AUSENTE en el body = no tocar el PIN existente (evita que un
  admin que re-guarda una patente por otro motivo borre sin querer un PIN ya cargado —
  distinto del comportamiento de `ownerName`, que sí se pisa siempre; acá la pérdida
  silenciosa de un PIN es un bug funcional real, no cosmético). Para BORRAR un PIN
  explícitamente: acción separada (`DELETE /admin/vehicles/:plate/pin` o
  `pin: null` explícito), nunca "dejar en blanco".

### 3. Lógica de negocio (`apps/api/src/services/machineService.ts`)
`categoryAndPriceOf` pasa a recibir el pin ingresado y el hash guardado:
```ts
function pinOk(vehicle: { pin: string | null } | null, providedPin?: string): boolean {
  if (!vehicle?.pin) return true; // grandfather clause: sin PIN seteado, no se exige
  return providedPin != null && verifySecret(providedPin, vehicle.pin);
}
```
Si `pinOk` es `false`, la patente cotiza como `externo` — MISMO camino que una patente no
registrada, sin excepción ni mensaje distinto (evita filtrar si la patente es o no
remis/socio a quien no tiene el PIN correcto). `quotePlate()` y `createSessionWithPayment()`
(en `sessionService.ts`, dentro de la misma transacción con lock advisory que ya existe)
llaman a la misma función — nunca puede haber diferencia entre lo cotizado y lo cobrado.

### 4. Rutas admin (`apps/api/src/http/routes/adminRoutes.ts`, `services/adminService.ts`)
- `upsertAdminVehicle`: hashea el pin SOLO si vino en el body; si no vino, no toca la
  columna (`onConflictDoUpdate` construye el `set` dinámicamente).
- Nueva acción explícita para borrar un PIN (checkbox "Quitar PIN" en la tabla → petición
  con `pin: null` explícito, distinto de "ausente").
- `listAdminVehicles`/`upsertAdminVehicle`: devuelven `hasPin` (booleano), nunca el hash.

### 5. Admin UI (`apps/web/src/admin/pages/VehiclesPage.tsx`)
- Form de alta: input PIN de 4 dígitos, opcional, junto a categoría/titular.
- Tabla: columna "PIN" (✓ configurado / — sin PIN) + botón "Quitar PIN" cuando hay uno.
- Texto de ayuda actualizado: mencionar que el mismo PIN se repite en las 2 patentes de una
  misma persona (remis + particular) para que comparta el beneficio.

### 6. Flujo del cliente (`apps/web/src/pages/MachinePage.tsx`)
- Input PIN (4 dígitos, opcional) junto al de patente, enviado en la MISMA request de
  `/quote` — no hay paso separado ni revelación previa de categoría antes de pedir el PIN
  (evita cualquier "esto es remis, ingresá tu PIN" que filtre el estado de una patente
  ajena). El precio mostrado siempre es el que se cobra.
- Mensaje estático (no condicional a la patente ingresada, para no filtrar nada) debajo del
  precio "particular": *"¿Sos socio o remisero? Verificá tu patente y PIN."* — ayuda a quien
  se olvidó de tipear el PIN sin revelar el estado de ninguna patente en particular.

## Phase 3: Eng Review — Dual Voices

**Claude subagent (segunda voz independiente, sin contexto previo — leyó el código real, no
mi resumen):** Verdict: Approve with changes — 2 fixes reales antes del Build, el resto
sólido.

> 1. **Inconsistencia schema/plan.** La Sección 2 (ahora corregida abajo) definía
> `pin: z.string().regex(/^\d{4}$/).optional()` en `VehicleUpsertSchema`, pero la Sección 4
> pedía mandar `pin: null` para borrarlo explícitamente — Zod's `.optional()` acepta
> `undefined` pero RECHAZA `null`, así que ese request fallaría validación tal como estaba
> escrito. Fix: `.nullable().optional()` + `upsertVehicle` necesita un tri-estado real
> (`undefined` = no tocar, `null` = borrar, string = hashear y setear) en vez del patrón
> "siempre pisa" que usa hoy `ownerName`.
> 2. **Sin protección específica contra fuerza bruta del PIN en `/quote`**
> (`publicRoutes.ts:27-31`, `middleware.ts:60-71`). Solo corre `createGlobalRateLimit()`
> (600 req/5min, ~2/seg por IP) — agotar el espacio de 10.000 PINs contra UNA patente
> conocida toma ~2.3 horas, sin lockout, sin límite por patente. Dado el incentivo
> económico real (hasta $6.000 de diferencia, ×2/día), es un camino realista, no teórico.
> Recomienda un contador de intentos fallidos POR PATENTE (no por IP).
>
> Todo lo demás cierra: el lock advisory + transacción en `sessionService.ts:91-135` alcanza
> para que cotización y cobro nunca diverjan por la lógica de resolución en sí (no protege
> contra una edición concurrente del admin a esa fila, pero ese TOCTOU ya existe hoy para
> categoría/precio, el PIN no lo empeora). Side-channel de timing en `verifySecret` (scrypt
> solo corre si hay PIN seteado) es real pero de severidad baja para este modelo de amenaza
> (lavadero de barrio, no un banco) — no bloqueante. Migración seguro (columna nullable sin
> default, ALTER de metadata). Alcance correctamente acotado, nada sobreconstruido.

**Auto-decisión (P5 explicit, ambos son hallazgos concretos con fix directo, no taste):**
se corrigen en el Build. La Sección 2 del plan (arriba) queda actualizada a
`.nullable().optional()` + tri-estado. Se agrega un rate limiter por patente
(`createPinAttemptRateLimit`, mismo mecanismo `express-rate-limit` ya usado en todo el
Mundo — reuso, no dependencia nueva) aplicado a `/quote` y `/sessions`, con `keyGenerator`
sobre la patente normalizada en vez de la IP.

## Fuera de alcance
- El cupo diario combinado por persona (si las 2 patentes de un socio deberían compartir un
  cupo de 2 lavados/día en vez de 2 cada una) — no lo pidió el cliente explícitamente y
  cambiaría ADR-024; se deja para una decisión aparte si surge.
- Entidad "socio" formal con gestión propia en el admin — ver alternativa descartada arriba.
- Cambios al flujo de reconciliación de pagos (ADR-033/034) o al deploy (ADR-035) — no
  relacionados.
