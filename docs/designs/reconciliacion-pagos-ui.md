## Problem Statement
Las 2 rutas backend de reconciliación de pagos (`POST /admin/sessions/:id/reconcile/auto`
y `/manual`, Fase 1 / ADR-033) están completas, probadas (91 tests verdes) y devuelven
mensajes en español ya redactados para mesa de entrada — pero hoy solo se pueden invocar
por `curl`. Mesa de entrada no tiene forma de usarlas en la operación real.

## Status Quo
Un cliente paga, el webhook de Mercado Pago se pierde o llega tarde (ADR-023), la sesión
pasa a `PAYMENT_EXPIRED` a los 600s (ADR-032) y queda trabada. Hoy, sin UI, la única forma
de recuperarla es que alguien con acceso a una terminal corra `curl` a mano siguiendo
`qa/FASE-1-manual.md` — en la práctica, nadie de mesa de entrada puede hacer esto solo.

## Premises
1. Es 100% trabajo de UI: las 2 rutas backend no se tocan.
2. El backend ya devuelve, en HTTP 200, un campo `message` en español listo para mostrar
   (`RECONCILE_MESSAGES` en `adminService.ts:487-502`) — la UI no redacta textos nuevos,
   solo los muestra.
3. El flujo manual exige que mesa de entrada tipee el ID real de pago de Mercado Pago
   (ADR-028: nunca un checkbox ciego) — la UI tiene que reflejar esa fricción, no
   simplificarla a un botón sin verificación.
4. Independiente de la política de reembolso y de ADR-007 (identidad de patente) — no
   bloquean este trabajo.
5. Solo el estado `PAYMENT_EXPIRED` es recuperable por esta vía (`isRecoverableTerminalStatus`,
   `paymentRecovery.ts:57` — type guard `status is 'PAYMENT_EXPIRED'`, los otros 7 estados
   terminales quedan excluidos por diseño desde ADR-029). La UI solo debe ofrecer la acción
   cuando el estado de la sesión es ese.

## Approaches Considered
### Approach A: Mínimo viable (ELEGIDA)
Agregar `PAYMENT_EXPIRED` al filtro de estado en `SessionsPage.tsx:59` (hoy no está en la
lista — gap de descubribilidad real, encontrado leyendo el código) + una card
"Reconciliación" en `SessionDetailPage.tsx`, visible solo cuando
`session.status === 'PAYMENT_EXPIRED'`, con: botón "Reintentar automático" (llama
`/reconcile/auto` sin input) y un form de una línea (input ID de pago MP + botón) para
`/reconcile/manual`. Reusa el patrón ya existente en `VehiclesPage.tsx` (estado
busy/error/saved, clases `.input`/`.btn`, `ApiError`) — mismo look que el resto del panel,
JSX inline dentro de la página, no un componente nuevo. Cero rutas nuevas.

**Post-acción y doble-submit (precisado tras revisión adversarial):**
`SessionDetailPage.tsx:62` ya usa `usePolling(load, 2000)` — la sesión se re-consulta sola
cada 2s. No hace falta código de refetch nuevo: si `/reconcile/auto` o `/manual` resuelve a
`approved`, el próximo poll trae `status` distinto de `PAYMENT_EXPIRED` y la card de
reconciliación desaparece sola (misma condición de visibilidad). Cada botón (auto y el
submit del form manual) se deshabilita mientras su propio request está en vuelo, calcado del
`disabled={busy || ...}` de `VehiclesPage.tsx:99` — evita el doble-click durante el request,
no bloquea reintentar después de una respuesta no resolutoria (`not_found`, `pending`, etc.),
que es el comportamiento correcto: el backend ya es idempotente ante reintentos
(`duplicated` si ya se resolvió antes).

**Form manual, specs de UI:** label "ID de pago (Mercado Pago)", placeholder de ejemplo
(`Ej: 1330000000`), sin validación de formato en el cliente más allá de no-vacío — mismo
criterio que `VehiclesPage.tsx` (el backend valida con el mismo `PaymentReconcileManualSchema`
que usa la ruta, `min(1).max(64)`); el submit queda deshabilitado si el input está vacío o
si hay un request en vuelo. Texto de los botones: "Reintentar automático" (acción auto) y
"Aprobar con este ID de pago" (submit del form manual).

**Errores de red/servidor (no HTTP 200 con `result`):** mismo patrón try/catch que
`VehiclesPage.tsx:51-52` — `err instanceof ApiError ? err.message : 'Error al reconciliar. Reintentá.'`.
`ApiError.message` ya trae el texto que arma `apps/api` para 401/403/500/validación
(`http/middleware.ts:errorHandler`, no se toca); el fallback genérico cubre timeout/red caída, casos sin
cuerpo JSON de error. Esto es el único texto nuevo en español de todo este trabajo — la
premisa 2 ("no se inventan textos nuevos") aplica a los resultados de negocio (`result`/
`message` del backend), no a este fallback de infraestructura, que ya es el mismo que usa
el resto del panel.

### Approach B: Arquitectura ideal
Todo lo de A, más una página nueva `/admin/reconciliation`: cola dedicada de sesiones
`PAYMENT_EXPIRED` con acciones inline por fila y contador en el nav. Evita que mesa de
entrada necesite encontrar la sesión a mano. Descartada por ahora: sin datos de volumen
real de cuántas reconciliaciones por semana ocurren (la fase recién cerró, ADR-033), es
prematuro construir una cola dedicada — si el volumen lo justifica, se promueve después
(la infraestructura de filtro por estado que Approach A agrega es la base que reusaría).

### Approach C: Lateral — acciones inline en la tabla de sesiones
Botones directo en las filas de `SessionsPage.tsx`, sin entrar al detalle. Descartada: el
input de ID de pago manual (ADR-028) no entra bien en una fila de tabla sin un modal o fila
expandible — agrega complejidad de UI sin ahorrar un click real (mesa de entrada ya termina
en el detalle para ver el timeline y confirmar que es la sesión correcta antes de reconciliar).

## Recommended Approach
Approach A. Cierra la brecha real (backend listo, sin forma de usarlo) con el menor diff
posible, reusando el 100% de los patrones de UI ya existentes en el panel. Si el volumen de
uso real justifica una cola dedicada, Approach B se construye después sobre la misma base
(el filtro de estado ya estará ahí).

## Open Questions
Ninguna bloqueante para el Build de esta pieza. La UI de "cola dedicada" (Approach B) queda
en backlog, condicionada a volumen de uso real — no es una pregunta abierta, es una decisión
explícita de no construir todavía.

## Success Criteria
- Mesa de entrada puede filtrar Sesiones por `PAYMENT_EXPIRED` y encontrar el caso sin saber
  el ID de sesión de memoria.
- Desde el detalle de una sesión `PAYMENT_EXPIRED`, un click reintenta la reconciliación
  automática; si no alcanza, un form corto permite tipear el ID de pago de MP.
- Todo resultado (`approved`, `not_found`, `pending`, `machine_occupied`,
  `machine_used_since`, `default_admin_forbidden`, etc.) se muestra con el mensaje que ya
  devuelve el backend — sin textos nuevos inventados en el frontend.
- Si el resultado es `approved`, la card de reconciliación desaparece sola en el próximo
  poll (2s) sin código de refetch adicional — la condición de visibilidad ya depende de
  `session.status`, que el polling existente mantiene actualizado.
- `npm run check` (`tsc` en las 4 workspaces) limpio; no se tocan tests de `apps/api`
  (esta pieza es solo `apps/web`).

## Dependencies
Ninguna de código — el backend de Fase 1 (ADR-033) ya está construido, probado y pusheado
a `main`. **Sí hay una dependencia de negocio que el /autoplan (voz CEO) señaló y que este
código no resuelve:** mesa de entrada todavía no tiene cuentas `admin_users` individuales
(`pendientes-manual.md` §3, pendiente del dueño) — el login compartido por defecto está
bloqueado a propósito para reconciliar (`default_admin_forbidden`, ADR-028/029). Esta UI
queda construida y correcta pero **sin uso real** hasta que esas cuentas existan. No bloquea
el Build (es la misma situación que ya tenía el Fase 1 backend); sí es la razón por la que
"cerrar esta pieza en el código" no equivale a "mesa de entrada ya puede reconciliar".

## The Assignment
Después del Build: abrir `/admin/sessions` en el navegador, filtrar por `PAYMENT_EXPIRED`
(usar el simulador de pagos demo para generar un caso si no hay uno real a mano), entrar al
detalle y confirmar que los dos botones aparecen y muestran el mensaje correcto.

   same type — a typo or a future renamed variant becomes a `tsc` error in both
   workspaces, which is this plan's only realistic safety net given zero frontend test
   infra exists (see #5 below).

3. **[MEDIUM] Card can unmount mid-flight if another admin or the sweep resolves the
   session while a manual submit is in flight** — the response (e.g.
   `session_id_mismatch` for a mistyped ID) renders into a card that's no longer
   mounted, silently dropping the feedback. **Auto-decision: documented risk, no code
   change (P3 pragmatic)** — building state that survives a parent re-render for a race

   error shown," not a wrong action taken (the backend transaction still resolves
   correctly either way).

4. **[LOW, verified safe] Rapid double-click / double-Enter isn't guarded by React
   state alone (`disabled` isn't synchronous), but `processApproval` runs inside one DB

   UI fix needed; noted so Build doesn't "fix" something the backend already guarantees.

5. **Tests: confirmed zero frontend test infra (`apps/web` has no `*.test.tsx`, no
   vitest config).** Building one for a 2-file card is disproportionate (P3). Given that,

   automated net this plan can reasonably have. Manual coverage instead: `qa/FASE-1-manual.md`

6. **Architecture/Security: sound.** No new endpoints, no new attack surface — hits the
   existing JWT-gated `requireAdmin` route (`adminRoutes.ts:44`) unchanged. `ApiError`
   reused unchanged.
