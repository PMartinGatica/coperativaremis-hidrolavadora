## Problem Statement
Pablo (dueño) quiere mandarle a SU cliente (la cooperativa de remises) un link real donde
vea el producto funcionando — no `curl`, no capturas, un link que se abra en el navegador.
Vio `hidro-api.insolvadev.com` y preguntó si ya sirve para eso.

## Status Quo (verificado en vivo, no supuesto)
- `curl https://hidro-api.insolvadev.com/` → `404 page not found` (Traefik). Confirma lo que
  ya documentaba `docs/deploy-coolify.md`: la red (túnel + DNS + Traefik) está viva desde el
  2026-09-04 (ADR-021), pero **la app en Coolify nunca se creó**. Nada corre ahí todavía.
- Aunque se cree la app hoy mismo con la guía tal como está escrita, seguiría sin verse nada
  visual: el `Dockerfile` de la raíz (leído completo) solo copia `apps/api/dist` a la imagen
  de runtime (líneas 27-32) y `apps/api/src/index.ts`/`app.ts` no tienen ningún
  `express.static` ni referencia a `apps/web` — confirmado por grep, cero resultados. La API
  y la web son procesos/artefactos separados hoy; el Dockerfile solo empaqueta uno.
- `apps/web` (un solo React Router app, `App.tsx:22-29`) cubre TODO el producto visual: el
  flujo del cliente (`/`, `/machine/:machineId`, `/pay/:externalId`, `/demo/device`) y el
  panel admin (`/admin/*`, con la UI de reconciliación recién construida). No hay dos apps
  separadas para cliente vs. admin.
- `npm run build` en la raíz (`package.json:14`) ya construye ambos en orden correcto
  (`shared → state-machine → api → web`) — el Dockerfile YA corre ese build completo en el
  stage `build` (línea 13), pero descarta `apps/web/dist` al armar el stage de runtime.

## Premises
1. Un solo dominio, un solo proceso — no se crea una segunda app en Coolify ni un segundo
   túnel (R1 del Universo: "no se crea un segundo túnel"). `apps/api` sirve el estático.
2. Cero dependencias nuevas — Express ya tiene `express.static` en su core, no hace falta
   instalar nada.
3. Cero cambios de comportamiento para quien corre `apps/api` sin haber buildeado `apps/web`
   (dev local, tests, CI): si `apps/web/dist/index.html` no existe, se mantiene el `GET /`
   JSON actual sin romper nada existente.
4. No se toca ninguna ruta `/api/*` ni `/health` — todas siguen devolviendo exactamente lo
   mismo que hoy (montadas primero en `app.ts`, el estático se agrega después).
5. Crear la app en Coolify sigue siendo acción de Pablo — sin acceso propio (confirmado en
   `pendientes-manual.md` §4). Este trabajo deja el repo listo para que ese paso, cuando se
   haga, ya sirva el producto completo.

## Approaches Considered

### Approach A: apps/api sirve el estático de apps/web (ELEGIDA)
`app.ts` monta `express.static(apps/web/dist)` + un catch-all `GET` (regex que excluye
`/api/*` y `/health`) que devuelve `index.html` para soportar el ruteo client-side de React
Router (`/machine/:id`, `/admin/*`, etc. tienen que servir el mismo `index.html` y dejar que
React Router resuelva). El Dockerfile copia `apps/web/dist` al stage de runtime. Un solo
dominio (`hidro-api.insolvadev.com`), un solo proceso, cero infraestructura nueva.
- Effort: S (CC: ~20 min) — 2 archivos (`app.ts`, `Dockerfile`), sin dependencias nuevas.
- Riesgo: Bajo. `express.static` no permite path traversal (usa `path.resolve` + chequeo de
  límites internamente); el catch-all está acotado por regex a rutas que no son `/api/`
  ni `/health`, así que un 404 real de la API sigue devolviendo JSON, no HTML.
- Reusa: el build ya existente (`npm run build`), cero componentes/rutas nuevas del lado web.

### Approach B: segunda app en Coolify solo para el estático (Nginx/Caddy o Coolify static-site)
`apps/web/dist` se sirve desde una app de Coolify separada (tipo "static site"), con su
propio subdominio o el mismo dominio con un router de Traefik por path. La API queda en
`hidro-api.insolvadev.com` tal cual está.
- Effort: M (human: Pablo crea 2 apps en Coolify en vez de 1 + configura el router de
  Traefik para que un mismo dominio reparta por path, o usa un subdominio nuevo).
- Riesgo: Medio. Dos despliegues para mantener sincronizados; CORS entre subdominios si se
  usa uno nuevo (hoy `corsOrigins` ya lista orígenes explícitos, habría que agregar uno más);
  más superficie de configuración de Traefik para algo que Express resuelve gratis.
- Reusa: nada nuevo del lado código, pero no reusa la simplicidad de "un solo deploy".

### Approach C: hosting estático externo (Cloudflare Pages / Netlify) para apps/web
Se despliega `apps/web` en un servicio de estáticos aparte, apuntando su `PUBLIC_API_URL` a
`hidro-api.insolvadev.com`. La API sigue como está.
- Effort: M (human: cuenta nueva en un proveedor externo, variables de entorno de build ahí).
- Riesgo: Medio — nuevo proveedor externo para un Mundo que ya decidió (R8/R1 del Universo)
  minimizar infraestructura dispersa; introduce un tercer sistema a mantener (Coolify + el
  túnel + este proveedor) para un problema que Express resuelve sin salir del repo.
- Reusa: nada del pipeline de deploy ya construido y documentado (`docs/deploy-coolify.md`).

**RECOMENDACIÓN: Approach A.** Es la opción de menor blast radius (2 archivos, sin
dependencias, sin infraestructura nueva), no reabre R1 (un solo túnel) ni agrega un proveedor
externo, y dado el objetivo declarado ("enviar rápido", intrapreneurship) es la que llega
primero a un link real. B y C tienen mérito solo si el tráfico de estáticos algún día
justifica separarlo de la API — no es el caso de un panel admin + flujo de pago de una sola
máquina.

## Plan de implementación
1. `apps/api/src/app.ts`: si `apps/web/dist/index.html` existe (resuelto vía
   `import.meta.url`, no `process.cwd()` — para que funcione igual en dev local y en la
   imagen Docker sin importar desde dónde se lance el proceso), montar
   `express.static(webDistDir)` + catch-all `GET` (RegExp, no string pattern — evita
   problemas de sintaxis de wildcards entre versiones de Express) que sirve `index.html`
   para cualquier ruta que no empiece con `/api/` ni `/health`. Si no existe, mantener el
   `GET /` JSON actual sin cambios.
2. `Dockerfile`: agregar `COPY --from=build /app/apps/web/dist ./apps/web/dist` al stage de
   runtime (el build ya lo genera, solo falta copiarlo).
3. Verificar local: build completo, levantar `apps/api` con `NODE_ENV=production` apuntando
   al `dist` real (no al dev server de Vite) y confirmar en navegador real (Edge headless)
   que `/`, `/machine/:id`, `/admin` y `/admin/sessions/:id` cargan la SPA real, que
   `/api/public/...` y `/health` siguen devolviendo JSON sin cambios, y que no hay
   violaciones de CSP en consola (helmet con defaults — a verificar, no asumir).
4. `docs/deploy-coolify.md`: actualizar el paso 2 (ya no dice "Podés probar el `/health`,
   pero no hay interfaz visual" — ahora si hay) — una vez Pablo cree la app, el mismo link
   sirve todo.

## Test plan
- `tsc --noEmit` en `apps/api` (el cambio toca `app.ts`, cero tipos nuevos esperados).
- 84 tests existentes de `apps/api` sin tocar — ninguno ejercita rutas no-API, así que deben
  seguir en verde sin cambios (verificación de que no rompí nada, no cobertura nueva).
- Verificación manual obligatoria (regla del Universo: "para cambios de UI/frontend, probar
  en navegador antes de reportar terminado"): build completo + arranque en modo producción
  local + navegación real Edge headless a las 4 rutas del punto 3 arriba.
- Fuera de alcance de este test plan: el deploy real a Coolify (acción de Pablo, no
  reproducible desde acá sin sus credenciales).

## Out of scope
- Crear la app en Coolify (Pablo, sin acceso propio — pendientes-manual.md §4).
- `TRUST_PROXY` (ADR-022, ya documentado, no relacionado a este cambio).
- Cualquier cambio a `apps/web` en sí (rutas, componentes) — este trabajo es 100% de cómo se
  sirve el build ya existente, no qué contiene.

### Architecture (ASCII)
```
Browser ──GET /, /machine/:id, /admin/*──▶ Express (apps/api)
                                              │
                                    existsSync(web/dist/index.html)?
                                     ┌────────┴────────┐
                                    sí                 no
                                     │                  │
                          express.static(web/dist)   GET '/' → JSON guide (como hoy)
                          + catch-all → index.html    (dev local sin build, tests)
                                     │
                          React Router (client-side)
                          resuelve /machine/:id, /admin/*, etc.

Browser ──GET /api/*, /health──▶ Express routers existentes (sin cambios, primero en la cadena)
```
